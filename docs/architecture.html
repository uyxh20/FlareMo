How Schizo Diary works

A plain-English map of the whole app: what runs where, where every kind of data is kept, how entries get searched and remembered, and what the AI actually reads during the weekly review.

Last updated 2026-10-13 · describes main at commit 4ca0c19

At a glance

Schizo Diary is a fork of the open-source app FlareMo. It runs entirely on Cloudflare: one program (a "Worker") serves both the web pages and the API, and it keeps everything in Cloudflare's storage services. There is no server of your own to look after.

Two halves live side by side. The diary half comes from FlareMo: quick entries (called memos), tags, attachments, search and an AI "memory" layer. The planning half is fork-only: the cockpit board, goals and the weekly review.

Diary entries (memos)

Each entry is one row in the memos table. Here is what happens when you save one.

  1. The text is saved as Markdown in memos.content, with a visibility (private, protected or public) and a status (normal, archived, trashed or deleted). A small JSON field remembers things like whether it has a link or an open checkbox.
  2. Tags are pulled out. Every #tag in the text is lowercased and stored as its own row in memo_tags. Nested tags use a slash, like #health/gym.
  3. A copy of the old version is kept in memo_revisions on every edit, up to the 50 most recent per entry.
  4. The keyword index updates itself (memos_fts), so plain-text search sees the change at once.
  5. A "please index this" note is queued in embedding_tasks, in the same save. The semantic index is updated just after the response is sent (see Search).

Attachments

The file goes to R2; D1 keeps its name, size and type, and which entry it belongs to. Uploads never attached to an entry are cleaned up after 7 days.

Comments and links

A comment is itself a memo, linked to its parent in memo_relations. Links between entries live in the same table.

Deleting

Delete first moves an entry to the bin. After 30 days in the bin the nightly job deletes it for good, with its files and search vectors.

Code: packages/domain/src/memos-write.ts, tags.ts, revisions.ts, memos-lifecycle.ts; files in apps/worker/src/attachment-http.ts.

Search and vectors

There are two separate kinds of search, and they don't mix for diary entries.

Keyword search

Finds the exact words you type, using SQLite's built-in full-text index in D1. Always up to date. This is what the normal search box uses.

Semantic search

Finds entries that mean something similar, even with different words. Uses "embeddings": each piece of text is turned into a list of 1,024 numbers that captures its meaning.

Yes, entries are vectorized. Here is how.

  1. Queue. Every save adds a row to embedding_tasks. The text itself is not copied; it is re-read when the task runs, so the newest version is what gets indexed.
  2. Run. Tasks run in the background after any save request, and again in the nightly job. Up to 32 per run, 5 tries each.
  3. Cut into chunks. Long entries are split at line and sentence breaks into pieces of about 1,000 characters.
  4. Embed. Each chunk goes to the Workers AI model @cf/qwen/qwen3-embedding-0.6b, which returns 1,024 numbers.
  5. Store. The numbers go into the Vectorize index flaremo-memos, tagged only with the entry id and user id. No text is stored there.

A semantic search embeds your query the same way, asks Vectorize for the closest chunks, scores each entry by its best chunk, then double-checks every hit against D1 so trashed or someone else's entries never show. It returns 10 results by default.

Known gap, found while writing this page. On 2026-10-13 only 46 of 579 entries were in the semantic index; 533 were marked "not indexed", and the task queue was empty. The cause is in the code: importing data (packages/domain/src/import-export/import-data.ts) saves entries as "not indexed" without queueing an indexing task, and nothing sweeps those rows later. Keyword search is unaffected. The admin "rebuild embeddings" action (POST /api/app/admin/embeddings/rebuild) is the built-in way to fill the index. Memories are partly indexed too: 73 of 118.

Code: packages/domain/src/embedding-outbox.ts, embedding-processors.ts, embedding.ts, semantic-search.ts; route GET /api/app/search/semantic.

Memory and dreaming

Memories are short, standalone conclusions ("prefers morning workouts", "decided X") kept separately from the diary, mainly so AI agents can learn about you without rereading every entry. Each one has a kind (fact, preference, decision, lesson, event…), a confidence from 0 to 100, a trust level (inferred, observed, confirmed, locked) and a link back to the entry it came from.

How memories are made

Agents write them

An AI agent connected through /memory/mcp can save a memory directly with memory_remember.

Nightly "dreaming"

Every night the app rereads recent entries and proposes new memories. Nothing is extracted at the moment you save an entry.

One dreaming pass

  1. Picks users who wrote in the last 2 days (just you).
  2. Reads entries since the last dreaming run, or the last 24 hours: up to 20 entries plus 20 recent event memories, capped at 12,000 characters in total and 1,200 per entry.
  3. Asks the Workers AI model @cf/meta/llama-3.1-8b-instruct for up to 8 candidate memories.
  4. Saves at most 5 a day. Ones that sound like instructions wait for your review; facts you rejected in the last 30 days are blocked.
  5. On Mondays it also samples 30 confirmed facts and flags up to 3 that contradict each other.

When an agent asks to recall something, the app combines four searches (exact key, keyword, vector, and one hop of related memories), ranks them together, and favours confirmed and locked memories. Older event memories fade gradually over a year.

Code: apps/worker/src/memory-dreaming.ts, packages/domain/src/memory/ (consolidation, recall, maintenance); API /api/app/memory.

Weekly review: look back and look forward fork

The review page at /weekly-review has two halves. Look back is a short chat about last week that ends in scores and a summary entry. Look forward turns next week's goals into a plan on the board. On Saturday and Sunday it reviews the current week; Monday to Friday it reviews the week before.

What the AI reads

The context is rebuilt fresh from D1 on every AI call. Nothing is cached between calls.

What it does not read: memories, the vector search, or diary entries from earlier weeks. The look back only sees the one week, plus last week's summary as the bridge.

Which model answers

The first one that is configured wins:

  1. OpenRouter, if an OpenRouter key is set. Default model openai/gpt-6.1-sol, the most accurate in the October 2026 review eval, with zero data retention.
  2. Anthropic, if an Anthropic key is set. Default claude-sonnet-5-5.
  3. Workers AI otherwise: @cf/meta/llama-3.3-70b-instruct-fp8-fast, with the smaller 12,000-character diary budget.

Per docs/planning-cockpit-goals-review.md, the OpenRouter key is set on dev only, so live runs on Workers AI. If the AI fails, the page falls back to its own drafts.

Where the results go

  • Work in progress autosaves to planner_review, so you can leave and come back.
  • Finishing look back writes a normal diary entry tagged #vault-summary, and the scores, question and verdict to planner_week.
  • Finishing look forward saves next week's goals, links tasks to them and reorders To Do with the plan on top. Each step is recorded, so pressing it twice never creates a task twice.

Cockpit and task history fork

The cockpit at /cockpit is one board built on top of the original FlareMo tasks. A task's title, status, priority, due date and notes stay in the upstream tasks table. Everything the cockpit adds (start date, effort, position on the board, goal, comments) sits next to it in fork tables, joined by task id, so an upstream update can't break it.

BacklogTo do, not yet planned
To DoTo do, planned
DoingIn progress
DoneLast 14 days shown

Dropped tasks sit in their own list and stop raising overdue alerts. Dragging a card writes a single position key, so reordering stays cheap.

The history archive (the data flywheel)

planner_task_event is a permanent log of everything that happens to a task: created, planned, moved, effort or date changed, commented, dropped, deleted, restored and purged. It has no hard link to the tasks table, so when a task is purged from the bin its history stays. The purge event keeps a copy of the task's title and project name.

Rule: never weaken this archive. Comment events store only the comment id, never its text. Moving a card's position writes no event.

History is gathered by comparing the tasks table with a snapshot (planner_task_seen) each time the cockpit opens (at most every 30 seconds), and twice a night: once before and once after the bin is emptied, so a purge is always recorded.

Code: packages/domain/src/planner/ (columns, board-rank, plans, history-sync); apps/worker/src/routes/planner-api.ts; page apps/web/src/planner/cockpit-page.tsx.

Goals fork

Goals live in planner_goal and form a cascade, each level crossed with four pillars (stored as of, work, ai, health):

North star→Year→Quarter→Month→Week

Each goal has a title, a few lines of detail, a status (draft, active, contested, closed) and, once closed, a result (met, partial, missed). A task serves a goal through its goal_id. Reviewed weeks and their scores live in planner_week; goal clashes found by the check live in planner_goal_flag. The goals page is at /goals.

Code: packages/domain/src/planner/goals.ts; migration migrations/9005_planner_goals_review.sql.

Nightly jobs

Every day at 03:17 UTC the Worker runs one housekeeping pass, in this order. A failure in one step never stops the others.

  1. Run any queued data exports and team-member removals.
  2. Send pending webhooks.
  3. Memory upkeep: expire unanswered proposals after 14 days, re-check evidence, demote untouched "observed" memories after 90 days.
  4. Dreaming pass, plus the Monday contradiction check.
  5. Work through the semantic-index queue.
  6. Clean up orphaned attachments (up to 10,000 a night).
  7. Empty the bin of anything older than 30 days, with a planner history sync before and after.
  8. Delete expired export files, rebuild the hourly writing heatmap.
  9. Create "on this day" and overdue-task notifications.

Code: apps/worker/src/scheduled-tasks.ts.

Login, apps and MCP

Login uses the Better Auth library. In the browser you get a cookie that the page script can't read. Scripts, Memos phone apps and AI agents use a personal access token that starts with memos_pat_; each one can be revoked and expires within a year at most. Public sign-up is off. This is a single-user install.

Fork rules

This repo is a fork of realchendahuang/FlareMo and pulls in its updates regularly. To keep that painless, fork code lives in its own folders and upstream files only get the smallest possible hook into it.

Fork-owned places

  • apps/web/src/planner/, apps/web/src/fork/
  • packages/domain/src/planner/
  • packages/contracts/src/fork-brand.ts, planner-*.ts
  • migrations/9xxx_*.sql, scripts/fork/

What the fork changes

  • The name "Schizo Diary", swapped in at display time
  • Team projects, Projects and Articles hidden from the sidebar (still reachable by URL)
  • The # tag picker with scroll and autocomplete
  • Cockpit, goals and weekly review

Fork database changes only ever add things, never link to upstream tables, and use numbers from 9000 up. Small "wiring" tests fail if an upstream update drops one of the hooks.

Full list with undo steps: docs/fork-customizations.md; cockpit design: docs/planning-cockpit-implementation-plan.md.

Nothing deploys automatically when code is pushed. Changes go local, then dev, then you try them, then live only when you say "push to prod".

What a live deploy does

  1. Refuses unless the code is exactly what is on main.
  2. Rebuilds the private config from the template plus the live settings (secrets are never printed).
  3. Notes the current live version as the rollback target and saves a database Time Travel bookmark (kept 7 days on the free plan).
  4. Counts rows in every table.
  5. Applies new migrations, then deploys.
  6. Counts again and loads the site. If any table lost rows or the site errors, it switches the Worker back to the previous version on its own.

The dev clone copies live data table by table, replays any new migrations as a rehearsal, and fails if any row count doesn't match. Its safety guard only allows read commands against live.

Details: docs/fork-dev-environment.md.
